# G2b: таблицы кандидатов и общий бюджет сжатия

Задача: [#161](https://github.com/v1docq/FedCore/issues/161), [PR #140](https://github.com/v1docq/FedCore/pull/140). Основание — [утверждённая архитектура](COMPRESSION_GRAPH_PROPOSAL.md) и [раздельное исполнение G2a](IMPLEMENTATION_GRAPH_G2A.md).

## Решение и границы

Для каждого исходного оператора строится одна конечная таблица альтернатив. Рецепт, ранг, параметры метрики и представление являются свойствами альтернативы. Два метода одного оператора нельзя представить независимыми таблицами: распределитель должен выбрать одну замену этого оператора.

Таблицы закрепляются за одной исходной моделью, версией графа и калибровочными данными. В этом срезе варианты разных операторов оцениваются на фиксированном снимке исходной модели. Для ASVD это явно обозначенный суррогат по фиксированному снимку. Последовательное изменение входов следующего слоя после выбора предыдущего варианта не объявляется независимой кривой ошибки.

У всех альтернатив должна быть общая мера оценки. Ошибку weighted SVD в полной метрике и ошибку ASVD в диагональной метрике нельзя непосредственно сравнивать или складывать. Собственная метрика метода определяет его решение; общая оценка сравнивает уже полученные замены в одинаковом контексте. Сумма локальных ошибок служит суррогатом для распределения бюджета. Она не доказывает оптимальность качества или задержки всей сети.

Семейство рангов строится повторными вызовами проверенного решателя в исходной метрике. Канонические факторы уже полученного оператора не являются взвешенным ранговым семейством. Например, при

$$
W=\operatorname{diag}(10,1,0.1),\qquad C=\operatorname{diag}(0.01,100,1)
$$

взвешенное решение ранга 2 сохраняет первые два направления. Обычное усечение его канонической SVD до ранга 1 сохраняет первое направление с ошибкой $100.01$. Взвешенное решение ранга 1 сохраняет второе направление с ошибкой $1.01$.

## Выбор алгоритма

Используется действующий `allocate` из [allocation.py](../../fedcore/algorithm/low_rank/allocation.py). Новый слой отвечает за происхождение таблиц, контекст, построение реальных альтернатив и проверку результата. Второй распределитель не вводится.

| Вариант | Стоимость и свойства | Решение |
| --- | --- | --- |
| Полный перебор | Произведение числа альтернатив; простой независимый эталон для малых таблиц и связанных хранилищ | Сохранён как ограниченный путь существующего распределителя и отдельный тестовый эталон |
| Точный разреженный динамический поиск | Число состояний зависит от числа достижимых целых стоимостей; без округления бюджета и рангов | Сохранён для независимых стоимостей |
| Жадный выбор по отношению ошибки к стоимости | Дешевле, но не гарантирует оптимум конечной таблицы, особенно при общих хранилищах | Не добавляется без отдельного протокола сравнения |

Кандидатный план содержит метаданные и ссылки. Рабочие модели и тензоры статистик остаются у исполнителя и ограниченного хранилища G2a. Возвращаемая модель должна быть независима от исходной; применение набора замен проверяется до записи.

Затраты подготовки включают отдельное решение для каждой объявленной альтернативы. Повторное использование статистик сокращает число сборов наблюдений, но не отменяет решение и проверку вариантов. Кандидатные веса не должны бессрочно храниться в каталоге: выбранный вариант воспроизводится по его описанию. Эта стратегия уменьшает срок жизни рабочих моделей ценой повторного численного решения при применении. Ускорение подготовки или применения в этом этапе не заявляется.

Поддержка ограничена двумя существующими фиксированными рецептами и их CPU-возможностями. Ссылки на один модуль относятся к одной цели. Разные операторы с общим изменяемым параметром требуют согласованного преобразования; неподдержанные связи отклоняются. Произвольные связанные группы, последовательный пересчёт зависимых таблиц и эволюционные изменения графа остаются в последующих этапах.

По умолчанию разрешено не более 128 альтернатив на каталог; явный предел находится в диапазоне 1–4096. Проверка количества предшествует численным задачам. Этот предел не гарантирует малое число состояний динамического поиска: оно зависит от сетки и достижимых стоимостей. Для крупных каталогов требуется отдельная оценка затрат; неограниченный поиск здесь не заявляется. Границы памяти описывают именованные копии и рабочие буферы, а не жёсткий предел любых выделений внутри пользовательского `forward`.

## Единицы бюджета

`unit="bytes"` означает объём уникальных физических хранилищ параметров и буферов, включая неизменённые части модели. `unit="parameters"` сохраняет смысл существующего распределителя: число всех объявленных хранимых элементов, в том числе буферов, шкал и карт. Число элементов `nn.Parameter` приводится отдельно, когда оно отличается от этой величины.

Смещения, остатки, шкалы и неизменённые хранилища нельзя исключать из итогового бюджета. Общий базис или другое общее хранилище считается один раз. При экспорте повторно проверяется фактическое представление после загрузки. Объём тензорных хранилищ и размер файла с заголовками и служебными записями являются разными величинами.

Для представлений одного физического хранилища с разными типами данных байтовый бюджет определён однозначно. Число хранимых элементов в таком случае неоднозначно; режим `parameters` должен вернуть явный отказ вместо неявного выбора размера элемента. Остаток байтов, не образующий целое число элементов объявленного типа, также нельзя округлять вниз.

## Публичный вызов

Основные функции находятся в [candidate_graph.py](../../fedcore/algorithm/low_rank/candidate_graph.py), описание физических хранилищ — в [candidate_storage.py](../../fedcore/algorithm/low_rank/candidate_storage.py).

`GraphCandidate.metric_ref` является ссылкой внутри собственного фиксированного графа. Её полная идентичность задаётся парой `(candidate.graph.fingerprint, candidate.metric_ref)`. Одинаковое локальное имя узла у двух значений `alpha` не означает одинаковую метрику. Связь проверяется вместе с графом; отдельного общего хранилища метрик здесь нет.

```python
from fedcore.algorithm.low_rank.artifacts import StatisticsStore
from fedcore.algorithm.low_rank.candidate_graph import (
    CandidateRecipe, prepare_candidate_catalog, allocate_candidate_catalog,
    apply_candidate_allocation, verify_candidate_export,
)
from fedcore.algorithm.low_rank.allocation import BudgetInfeasible

store = StatisticsStore(max_bytes=64 * 1024**2)
try:
    catalog = prepare_candidate_catalog(
        model, calibration, graph_version="model-v1", store=store,
        alternatives={
            "encoder.linear": (
                CandidateRecipe("weighted_svd", rank=8),
                CandidateRecipe("asvd", rank=8),
                CandidateRecipe("weighted_svd", rank=16),
            ),
        },
    )
    plan = allocate_candidate_catalog(catalog, budget=1_000_000, unit="bytes")
    if not isinstance(plan, BudgetInfeasible):
        result = apply_candidate_allocation(model, calibration, plan, store=store)
        exported = verify_candidate_export(result, format="torch_save_module")
        # exported.model owns the loaded model; exported.evidence is metadata.
        # Evaluate this whole model on separate validation data before adoption.
finally:
    store.close()
```

Путь `encoder.linear`, ранги и бюджет в примере должны соответствовать вызывающей модели. Неосуществимый бюджет возвращается как `BudgetInfeasible`; он не увеличивается автоматически. Отказы контрактов имеют структурированные причины.

Внешний фасад `LowRankModel` предоставляет `prepare_candidate_catalog` и `compress_candidates`; распределение бюджета остаётся отдельной чистой функцией. После успешного применения фасад передаёт новую модель действующему владельцу, а связанный обучающий компонент получает требование пересобрать оптимизатор. Прежние вызовы `compress_graph`, `compress_weighted` и `compress_profile` сохраняются.

Каталог привязан также к полным хранилищам параметров и буферов, включая непостоянные буферы, смещения, шаги представлений и связи общего хранения. Эта информация входит в пространство имён статистик данного каталога. При изменении исходных данных, модели или этих связей старый план применять нельзя.

Контекст фиксирует также исходное состояние генераторов Python, NumPy и Torch CPU, использованное в ключах статистик. Изменение этого состояния до применения даёт явный отказ. Подготовка и применение сохраняют состояние генераторов вызывающего кода. Наблюдение должно сохранять модель, данные и режимы; обнаруженное изменение непостоянного буфера тоже отклоняется до публикации снимка.

В этом режиме состояние тензоров должно быть зарегистрировано в параметрах и буферах. Обнаруживаемые дополнительные ссылки на тензоры в атрибутах и стандартных контейнерах отклоняются: обычное копирование Python с последующим восстановлением связей хранилищ не обеспечивает их согласованность. Скрытое внешнее состояние произвольного `forward` по-прежнему требует явной версии графа и не становится автоматически проверяемым.

Сбор каталога использует отдельные транзакции проверенного исполнителя G2a. Если поздний вариант не удалось построить, каталог и частичная модель не возвращаются. Корректные снимки ранее завершённых вызовов могут остаться в ограниченном общем хранилище для повторного использования; транзакция неуспешного вызова откатывается. Очисткой и сроком жизни хранилища управляет вызывающий код.

`verify_candidate_export` проверяет фактическое сохранение и загрузку в явно указанном локальном формате `torch_save_module`. Этот результат не подтверждает допуск всех других форматов. Для TorchScript или другого целевого формата нужен отдельный экспорт и проверка загруженного артефакта.

## Проверки и результат

Сквозной [пример](../../examples/low_rank_ann/graph_candidate_budget.py) и его [численные результаты](results/graph-g2b-2026-10-19/result.json) проверяют всю последовательность: каталог → распределение → применение → сохранение и загрузка → TorchScript → оценка всей сети. Это функциональная проверка случайной MLP `12 → 10 → 6` с `Tanh`, а не эксперимент на обученной модели.

Генераторы Python, NumPy и Torch инициализируются числом 161; отдельные генераторы калибровочных и отложенных входов — числами 162 и 163. Калибровка содержит 64 строки, проверка — 128 других строк. Для каждого из двух Linear предлагаются ASVD и weighted SVD с рангами 1, 2 и 4. Бюджет задаётся до выбора; отложенные входы при выборе не используются.

| Величина | Результат |
| --- | --- |
| Исходные тензорные хранилища | 1568 байт |
| Заданный бюджет | 1024 байта |
| Выбор | weighted SVD, ранги 4 и 1, `two_layers` |
| Полученные тензорные хранилища | 960 байт |
| После загрузки локального формата и TorchScript | 960 байт |
| Локальная сумма квадратов ошибок на одно наблюдение | 0,9571397536 |
| MSE всей загруженной сети по 128 отложенным входам | 0,0423782691 |
| Задержка загруженного TorchScript, p50 / p95 | 0,03895 / 0,051005 мс на пакет из 16 строк |
| Размер файла TorchScript | 9773 байта |

Локальная сумма и MSE сети имеют разную нормировку и разный объект оценки. Они не подменяют друг друга. Время измерено существующим `measure_artifact`: CPU, float64, два потока, пять прогревочных и 30 измерительных вызовов, без параллельного обучения и тестов. Это проверка пути измерения; исходная модель в данном запуске по задержке не сравнивается, ускорение не утверждается. Файлы с моделями создаются локально; в Git сохраняются сценарий и JSON с протоколом и результатами.
