# G2a: исполнение узлов и повторное использование статистик

Дата: 19.10.2026. Задача: [#160](https://github.com/v1docq/FedCore/issues/160), [PR #140](https://github.com/v1docq/FedCore/pull/140), ветка `svd_compression`. Основа — [G0–G1](IMPLEMENTATION_GRAPH_G1.md); дальнейшие этапы описаны в [плане внедрения](COMPRESSION_GRAPH_ISSUES.md).

## Задача и граница

В G1 вершины описывали стадии, которые выполнялись внутри целого прежнего рецепта. Такой план проверял совместимость, но не позволял пропустить повторный сбор статистик. G2a добавляет явный режим `staged_fixed_recipe_v1`: исполнитель последовательно выполняет `OBSERVE`, `METRIC`, `SOLVE`, `BUILD` и `APPLY` по проверенному фиксированному плану.

Режим `checked_whole_recipe_v1` остаётся исходным значением по умолчанию. Новое исполнение подключается при подготовке плана. Свободная топология поиска, распределённое хранилище и таблицы вариантов под общий бюджет относятся к последующим задачам.

## Выбор хранилища

Сравнивались три варианта:

| Вариант | Стоимость и поведение | Решение |
| --- | --- | --- |
| Собирать заново | Снимки не занимают память между запусками; каждое наблюдение требует повторного `forward` | Сохраняется как проверочный вариант |
| Ограниченный словарь без вытеснения | Явный предел тензорных данных, отказ до нового сбора при нехватке места, стабильные ссылки до очистки | Выбран для G2a |
| LRU с вытеснением | Нужны правила устаревания ссылок и изменения порядка использования; освобождение места зависит от истории обращений | Отложен до появления измеренной потребности |

Записи хранят только запрошенные статистики. Для входного размера `d` статистика ASVD занимает `8d` байт в float64; нецентрированный второй момент — `8d²` байт на группу. Метрики, факторы, заменяемые модули и исходные наблюдения не сохраняются в этом хранилище. Для ASVD текущий ограниченный сбор строк сохраняет временную стоимость прежнего профиля; размер сохранённого вектора не является оценкой всей рабочей памяти.

Поиск записи использует словарь с обычной средней стоимостью обращения O(1); подготовка ключа включает проверку содержимого модели и данных. Она требует линейного чтения соответствующих тензоров. Ускорение всего преобразования из наличия словаря не следует: хеширование, копирование и численное решение могут преобладать.

## Происхождение и актуальность

`StatisticsKey` описывает фактический источник наблюдения, калибровочные данные, путь и область, вид статистики, нормировку, координаты, точность, версию оценщика и размер пакета. Отсутствие масок и весов указано явно: новый внешний API для них не добавляется. Идентификатор начального состояния генераторов случайных чисел также входит в ключ.

`StatisticRef` содержит метаданные ссылки. Чтение по ссылке с несовместимым ожидаемым происхождением возвращает структурированный отказ; старый снимок нельзя объявить статистикой новой версии.

В weighted SVD наблюдения закреплены за исходным снимком. В ASVD источник следующей статистики определяется после применения предыдущей замены. Поэтому изменение `alpha` допускает повторное использование средних модулей первого слоя, но может сделать статистики последующих слоёв непригодными. Для них выполняется новый сбор по новому ключу.

`alpha`, выбранный ранг и настройки метрики не входят в ключ исходной статистики сами по себе. Они входят в дальнейшие решения плана; если они изменили предшествующую модель, её фактический идентификатор меняется. Метрика после смены `alpha` строится заново.

Скрытое состояние произвольного пользовательского Python-кода автоматически не выводится из тензоров. Вызывающая сторона должна отражать такое состояние в `graph_version` и соблюдать контракт наблюдения.

## Наблюдения с эффектами

Пропуск `forward` на попадании в кэш меняет поведение, если сбор продвигает генератор случайных чисел, обновляет буфер модели или изменяет входной тензор. Поэтому новый режим требует наблюдения без таких эффектов.

Исполнитель сравнивает состояние до и после сбора. Обнаруженное изменение модели, калибровки, режимов модулей или Python/NumPy/PyTorch CPU RNG даёт `UnsupportedObservationEffect`; новые снимки запуска не публикуются. Проверки не доказывают чистоту произвольного кода с внешними эффектами. Прежний режим G1 сохраняет свой набор возможностей.

## Владение и время жизни

`StatisticsStore` владеет отделёнными снимками. При записи он отделяет тензоры от переданных значений, а публичное чтение возвращает отдельную копию. Изменение прочитанного тензора не портит общий снимок и соседние ветви.

Новые записи публикуются только после успеха всего преобразования. Отказ последующей стадии отменяет новые записи текущего запуска; ранее сохранённые снимки остаются доступными. `clear()` освобождает записи, `close()` завершает жизненный цикл хранилища.

После возврата результата сохраняются новая модель, ссылки `FixedGraphResult.statistic_refs`, фактический журнал стадий и статистики в переданном хранилище. В `evidence` ссылки представлены метаданными, пригодными для JSON. Промежуточные метрики, факторы и предложения замен не предоставляются как долговечные общедоступные объекты. Запись о выполненной стадии не означает, что любой её промежуточный тензор можно прочитать после завершения.

В журнале `actual_stages` для каждого узла указаны стадия, смысловой тип, ссылка на фактический результат, объём тензоров, признак повторного использования и число наблюдений через `forward`. Число проверочных вызовов учитывается отдельно. На попадании в хранилище `OBSERVE` получает существующий снимок; метрика и решение при этом вычисляются по текущему плану.

Поддержаны только три вида статистик двух фиксированных рецептов. Порядок-зависимый Gram EoRA не принимается как обычный сливаемый второй момент; его интерпретатор и правила повторного использования здесь не добавляются.

## Память и отказы

До сбора проверяются ёмкость хранилища и объявленные рабочие буферы. Отдельно учитываются копии модели и калибровки, накопители, метрики, решения, подготовленные замены и временные копии снимков. Ограничение хранилища относится к тензорным данным; оно не ограничивает накладные расходы объектов Python.

Проверка именованных буферов с резервом не обеспечивает жёсткую границу RSS для произвольного пользовательского `forward` или распределителя памяти. Недостаток ресурсов даёт явный отказ; автоматического повторного запуска с другими параметрами нет.

## Публичный вызов

```python
import torch
from torch import nn

from fedcore.algorithm.low_rank.artifacts import StatisticsStore
from fedcore.algorithm.low_rank.low_rank_opt import LowRankModel
from fedcore.algorithm.low_rank.method_specs import ASVD

torch.set_num_threads(2)
model = nn.Sequential(nn.Linear(8, 6), nn.ReLU(), nn.Linear(6, 4)).double().eval()
calibration = torch.randn(12, 8, dtype=torch.float64)
compressor = LowRankModel({"device": "cpu"})
store = StatisticsStore(max_bytes=1024**2)
try:
    plan = compressor.plan_compression_graph(
        model, calibration, recipe="asvd", method_spec=ASVD(alpha=0.5),
        rank=2, graph_version="example-v1", executor="staged_fixed_recipe_v1",
    )
    cold = compressor.compress_graph(model, calibration, plan, store=store)
    warm = compressor.compress_graph(model, calibration, plan, store=store)
    torch.testing.assert_close(cold.model(calibration), warm.model(calibration))
finally:
    store.close()
```

## Проверки

Окончательная целевая серия: **223 passed**, 3 предупреждения, 21,61 с. Она включает 100 новых тестов, прежние 88 проверок G1 и существующий набор взвешенного ядра. Два новых файла отдельно: **100 passed**, 6,03 с; из них 38 проверок реализации и 62 независимые проверки. Проверка wheel/sdist и установленного пакета отдельно: **1 passed**, 54,54 с. Эти наборы пересекаются; их числа не суммируются.

Локальный общий прогон пока **не прошёл** из-за описанного ниже нативного сбоя. Результат полного набора в чистых средах GitHub Actions фиксируется в [PR #140](https://github.com/v1docq/FedCore/pull/140).

В функциональном примере из `test_compression_graph_stages.py` используются два Linear `4 → 4 → 3`, 11 строк float64 и пакет из трёх строк:

| Рецепт | `forward` для наблюдений при сборе | При повторном использовании | Сравнение весов с прежним рецептом |
| --- | --- | --- | --- |
| weighted SVD | 8 | 0 | Точное равенство, `rtol=0`, `atol=0` |
| ASVD | 8 | 0 | Точное равенство, `rtol=0`, `atol=0` |

При изменении `alpha` в двухслойном ASVD первый снимок переиспользуется, а после изменённого первого оператора входы второго собираются заново. Отдельный аналитический пример показывает смену выбранного направления при той же абсолютной статистике. Эти проверки подтверждают корректность исполнения и повторного использования. Сокращение числа наблюдений само по себе не доказывает ускорение всего преобразования.

Проверки включают:

- сравнение выходов и весов с прямыми вызовами прежних рецептов, отдельно со сбором и повторным использованием;
- независимые формулы `XᵀX/N`, среднего и максимального модуля, а также согласованность накопления и объединения частей;
- модель состояний хранилища с ограниченной ёмкостью, очисткой, завершением работы и повторными обращениями;
- изменение `alpha`, перестроение метрики и пересборку статистик после изменённого предшественника;
- отказы при смене происхождения, недостатке памяти, ошибке последующего решения и обнаруженном эффекте `forward`;
- фактический порядок стадий, число вызовов `forward`, сохранность модели, данных, генераторов случайных чисел и hooks;
- запись свидетельств в JSON и запуск публичного API из установленного wheel.

При проверке новой реализации исправлены следующие пробелы:

1. Доступ к внутреннему снимку через первоначальный интерфейс транзакции позволял менять общий тензор. Транзакция стала внутренним механизмом исполнителя; публичное чтение отделяет данные.
2. Незавершённое резервирование могло исказить счётчик байтов. Перед публикацией теперь проверяется соответствие всех резервов готовым снимкам.
3. Перенос старого снимка под новый ключ не сверял его паспорт. Запись проверяет согласованность ключа, паспорта, вида и формы статистики.
4. Первоначальный журнал содержал объекты ссылок, непригодные для JSON. Типизированные ссылки вынесены в результат; журнал содержит переносимые метаданные.
5. Предварительные оценки копий и решателя не складывались. Теперь проверяются совместно живые буферы и дополнительные выделения отдельных стадий. Для ASVD отдельно учитываются временные буферы вычисления абсолютной статистики по собранным строкам.
6. Ошибка выделения памяти при копировании снимка выходила из публичного хранилища как обычный `MemoryError`. Теперь она преобразуется в структурированный `ResourceLimitExceeded`; транзакция отменяется без повторного запуска.

Первый общий запуск без ограничения числа потоков прервался с Windows access violation, код `0xC0000005`, во время ожидания подпроцесса проверки установленного пакета. Первопричина пока не установлена; изменение числа потоков не устранило сбой, и исправление нативной проблемы Windows не утверждается. Локальная среда использует Python 3.10.0 и доступ к общим системным пакетам; сравнение с GitHub Actions служит отдельной проверкой совместимости, а не доказательством причины.
