# Объединение Sparse и SVD

Дата: 21.10.2026. Интеграционная ветка: `integration/svd-sparse`; целевая ветка PR — `svd_compression`. Задача — объединить опубликованную CPU-реализацию Sparse с актуальным PR #140, сохранив исходные рабочие копии и прежние контракты. Экспериментальные серии и кластерные задания не запускались.

## Исходные версии и сохранность работы

| Источник | Закреплённый коммит |
| --- | --- |
| SVD / PR #140 | `cd29823122f9454772ebde0aede3eabaa2977cd4` |
| Опубликованный Sparse | `59028b228983a8a46bff8272e59c7aacfeee7916` |
| Общая база | `844114fc968c436e030b93e4ccac6f954ae76ff0` |

Опубликованная версия Sparse включает три коммита: реализации профилей, BERT v1 и численное исправление с результатами v2. Эти изменения сохраняются вместе с историей; старая локальная копия и её незавершённые SVD-правки не переносятся поверх интеграции.

Интеграция выполнена в отдельном Git worktree. До изменений записаны HEAD, статус и хеши изменённых/неотслеживаемых файлов трёх исходных копий. В старой копии учтено 130 файлов; в начале две актуальные копии были чистыми. Завершающая сверка и её паспорт приведены в каталоге результатов этой интеграции.

## Изменения при объединении

Единственный текстовый конфликт возник в `tests/refactoring/test_core_packaging.py`. Сохранены оба списка обязательных модулей, проверки SVD/G0–G5 и проверки Sparse. Внешний контракт включает версии `(1, 2, 3, 4)`; v4 означает версию внешнего запроса, а не новый общий формат файлов контрольных точек.

`ExperimentRunner` сохраняет существующие пути исполнения SVD, weighted SVD и P2, а также `drop_last`, добавляя отдельную диспетчеризацию Sparse-профилей. Публичные `LowRankModel` и `BasePruner.compress_profile` продолжают действовать в своих объявленных границах.

При независимом чтении обнаружен дефект физического хранения: общий участок памяти между параметром одного семейства и буфером Sparse-оператора не виден при учёте связей только между объектами `Parameter`. Копирование либо поэлементное клонирование при сохранении могло молча разделить такое хранилище и изменить объём физического хранения.

Добавлена узкая `validate_sparse_storage`:

- проверяет зарегистрированные параметры и буферы графа, включая непостоянные;
- запрещает неподдержанные связи Parameter↔Buffer и разные Tensor-представления общего хранилища, затрагивающие Sparse;
- отклоняет Sparse-состояние со смещением или лишними байтами исходного хранилища до копирования/присваивания;
- сохраняет поддержанные общие объекты Parameter, Buffer и модулей;
- применяется перед преобразованием Sparse, weighted/P2, копированием в runner, описанием контрольной точки и восстановлением её состояния.

Ошибки границы превращаются в существующие доменные отказы. Математика LoSparse v2, его расписание, численные допуски и решатели Sparse не менялись. Профиль G5 по-прежнему заранее отклоняет физические Sparse-операторы.

Целевые проверки выявили ещё один дефект: фабрика `FactorizedLinear` заменяла дочерние слои на `nn.Linear` с типом `float32`, хотя описание задавало `float64`. Восстановление общей основы переносило такой слой в Sparse-ветвь, где строгая проверка правильно отклоняла несовпадение. Фабрика теперь приводит дочерние слои к объявленному типу до восстановления связей. Проверка типов остаётся строгой.

## Проверки и упаковка

Новый `test_svd_sparse_coexistence.py` содержит 41 параметризованный случай: смешанные Factorized/Remapped/PackedNM/Indexed-модели, точные выходы после восстановления, общие объекты, смещения, координаты, физический инвентарь, повреждённые состояния, отказы до эффектов, оба порядка публичных преобразований, runner и внешние версии v1–v4.

Двадцать восемь чистых численных случаев LoSparse перенесены из LLM-теста в независимый CPU-модуль. Оставшийся BERT-тест проверяет необязательный `transformers` до импорта. Это сохраняет базовый CPU-набор без LLM-зависимостей, не скрывая от него упаковку и точность инициализации LoSparse.

CI теперь запускается и для PR в `svd_compression`. Отдельное задание `optional-llm` устанавливает уже объявленный дополнительный набор `llm` и выполняет BERT/Llama/Mixtral-проверки без сети и скачивания моделей. Существующие Linux/Windows, Python 3.10/3.11, упаковка и дополнительные экспортные/сервисные проверки сохранены.

Для локальной проверки создана отдельная среда: Python 3.10.0, PyTorch 2.2.0+cpu, Transformers 4.44.2. Основные зависимости читаются из прежнего CPU-окружения без его изменения, дополнительные LLM-пакеты установлены только в новый каталог. `pip check` завершился успешно. Вычисления ограничены CPU и тестовыми синтетическими данными; исторические модели BERT/Digits и их научные серии не повторялись.

Исходный целевой прогон сохранён отдельно: 202 теста прошли, три завершились ошибкой. Два выявили описанный дефект типа данных; третий — слишком широкую область подмены `copy.deepcopy` в новом тесте раннего отказа. После исправлений повторена вся целевая серия из 205 случаев. Исходный неуспешный журнал не заменён итоговым.

## Исторические результаты и ограничения

Сохранены [отчёт Sparse v1](../sparse_compression/LOCAL_EXPERIMENT_RESULTS.md), [протокол v2](../sparse_compression/LOCAL_EXPERIMENT_PROTOCOL_V2.md), [результаты v2](../sparse_compression/RESULTS_V2.md) и переносимые численные сводки. Во v2 все 15 компактных вариантов прошли технические проверки, но ни один не сохранил качество в заранее заданном пределе. Этот отрицательный результат не переименован в успешное сжатие.

Файлы протоколов и исторических численных свидетельств получили явные правила окончания строк: опубликованный хеш протокола v2 `4509a689ea599e00f45b0cee03e8f0507266ad664c0da0f51b5423cb1f9750fa` сохраняется и в Windows checkout. Карта issues исправлена: PruneNet — #153, отложенный TEDEPR — #154.

Объединение не добавляет Sparse в поисковое пространство G3/G5, не создаёт CUDA sparse/INT8-ядра и не расширяет профиль на произвольный Conv, ResNet или ViT. Эти задачи остаются следующим этапом. Терминальный RSS-сбой остановленного local3 также не исправляется попутно и не является основанием для повторного запуска.

Связанные задачи: #141–#156, PR #140. Наличие кода и этого PR не закрывает автоматически всю исследовательскую серию. Слияние интеграционной ветки в SVD выполняется после проверки окончательного коммита и CI.

Использованы `fedot-refactor-router`, `fedot-invariant-tests-review` и независимое чтение контрактов; финальная редактура русского текста — `edit-russian-technical-text`. OpenResearch/orx не подключался.
