# Проверка размещения Q/DQ на A100

Цель — проверить, сходятся ли логиты ONNX Runtime и TensorRT после удаления выходной пары Q/DQ у `layer1.0.conv1`. Сравнение использует сохранённый Q-only после 200 шагов восстановления. Оно отделяет изменение функции ONNX от расхождения двух исполнителей.

## Что подготовлено на CPU

Вариант строится из исходного Q-only ONNX. Подготовительный скрипт удаляет только два узла перед ReLU, их масштаб и нулевую точку, затем подключает к ReLU прямой выход Conv. Проверка сверяет все оставшиеся узлы и инициализаторы, вход `images`, выход `logits` и метаданные модели. Входные Q/DQ, INT8-веса и FP32-смещения всех выбранных свёрток подтверждены. SHA-256 нового ONNX — `762231509175d9038cb19236981ee706714d4dbf17504b66dfb1ac2055bd26cd`.

На восьми сохранённых калибровочных входах исходный ORT побитно воспроизвёл архивные логиты в пакетах 2 и 6. Между графами изменились все 80 логитов, максимальная абсолютная разница составила 0,7761, средняя — 0,1303. Предсказанный класс изменился у четырёх из восьми изображений. Восемь входов включают шесть ранее выбранных расхождений и служат для диагностики. Оценка качества по ним не проводится. [Данные проверки](validation/placement-admission-preparation-2026-11-06/CPU_PREPARATION.json).

Локально прошли 163 теста, два теста с реальными процессами Linux пропущены на Windows. Проверены прежние профили диагностики, пределы нового профиля, остановка до сборки при расхождении контроля, ранний численный отказ и завершение процесса с подставной телеметрией.

## Порядок и предел запуска

1. Перед выделенным окном проверить чистую ревизию, исходные SHA-256 ONNX и engine, хеш нового графа и версии. На целевом Linux отдельно провести CPU-проверку цепочки GNU timeout → supervisor → guard → рабочий процесс с подставной телеметрией, включая выход дольше 0,25 с и освобождение GPU до получения кода завершения. Этот допуск остаётся обязательным.
2. В начале окна подтвердить пустую A100 40 ГБ по прежнему UUID и действующий внешний срок GNU timeout. Рабочий процесс сверяет тот же UUID до TensorRT. Контейнер подтверждает одну стабильную строку NVML и её связь по времени с собственным процессом, поэтому `host_pid_identity_proven=false`.
3. На исходных ONNX и сохранённом engine повторить прежний пакет из двух входов. Оба набора логитов и вход должны побитно совпасть с архивом, где было шесть нарушений. После этого проверить конечность логитов нового ONNX на тех же входах. При отказе сборка не начинается.
4. Собрать **один** новый engine в TensorRT 10.0.1 с исходным профилем batch 1/128/128, рабочей областью 1 ГиБ и отключённым TF32. Заново загрузить файл и подтвердить через инспектор все 16 выбранных INT8-свёрток. Затем сравнить его логиты с ORT нового графа. Если на первых двух входах есть нарушение допуска, завершить численный этап с сохранением результата.
5. Если первые два входа прошли, обработать оставшиеся калибровочные пакеты в прежнем порядке. Для каждого пакета сохранить четыре набора логитов. Сравнить TensorRT с ORT отдельно для каждого графа, а изменение вычисляемой функции оценить по паре ONNX Runtime. Первый пакет 128 выполняется после сборки. Для него и следующих пакетов сохраняются фактические результаты контрольного движка.

| Предел | Значение |
|---|---:|
| Внешнее окно, включая завершение | 600 с |
| Рабочее окно от исходного старта | 540 с |
| Сборки TensorRT | 1 |
| Различные калибровочные изображения | до 2000 |
| Пакеты | 2 + 15 × 128 + 78 |
| Вызовы инференса в четырёх сочетаниях | до 68 |
| Строки с учётом повторов | до 8000 |
| Шаги SGD, поиск, повторная калибровка и автоматические повторы | 0 |

Исполнитель восстанавливает прежнее стратифицированное разбиение из зафиксированного train-корпуса и сверяет отпечатки. Инференс использует только роль calibration. Метки не участвуют в численном сравнении. Vsearch, Vreport и официальный test не оцениваются. Наблюдатель останавливает запуск, если снимок показывает более 16 ГиБ GPU-памяти, более 32 ГиБ RSS дерева или менее 100 ГиБ свободного диска.

Счётчики диагностического запуска фиксирует `actual_budget` в квитанции. `config.json` служит для передачи внешнего срока и параметров надзора через общий формат пилота.

## Как трактовать результат

Для допуска нового engine требуется независимая загрузка, подтверждение 16 INT8-свёрток и выполнение условия `abs(TRT − ORT) ≤ 0.02 + 0.02 × abs(ORT)` на всех 20 000 логитах нового графа. Максимальная и средняя ошибки, число нарушений и совпадение предсказанных классов сохраняются вместе с сырыми логитами. Пара ORT показывает изменение функции и имеет описательный статус.

Контрольный engine взят из пилота. Он отвечает за воспроизводимость прежнего отказа, а единственная новая сборка проверяет допуск конкретного нового engine. Различия тактик TensorRT остаются возможным объяснением различий между движками. Выходы графа не дополняются отладочными тензорами.

После сохранения квитанции guard ждёт фактический код завершения своего процесса до 10 секунд внутри рабочего срока. Допустим только переход прежней строки NVML к пустому списку. Чужая или повторно появившаяся строка, нарушение хешей, версии, сроков, счётчиков и размеров прерывают допуск. Для успешного завершения необходимы коды 0 рабочего процесса, guard и supervisor, очистка без принудительных сигналов и пустая телеметрия по тому же UUID после очистки.

Этот опыт даёт аппаратную проверку конкретной пары граф и движок. Приёмка исходного Q-only, проверка качества и завершение пилота остаются отдельными этапами. Из 7200 с исходного бюджета числятся 5965,25 с. Одно предложенное окно 600 с входит в этот остаток. Запуск требует отдельного разрешения.

## Точки входа

Подготовка ONNX выполняется на CPU.

```powershell
python scripts/prepare_heterogeneous_qonly_placement.py --source-model <saved-model.onnx> --source-engine <saved-model.engine> --output-directory <fresh-directory>
```

Команда проверки надзора на целевом Linux. Тест запускает реальные процессы с подставной телеметрией.

```bash
python -m pytest -q tests/refactoring/test_heterogeneous_placement_admission.py::test_placement_supervision_linux_cpu_terminal_handoff
```

Будущий запуск использует `scripts/run_heterogeneous_qonly_diagnostic.py` с профилем `placement_v1`, полным SHA чистого коммита, абсолютными путями к исходному каталогу Q-only и новому ONNX. Профиль фиксирует 2000 строк и batch 128. В свежем каталоге сохраняются журнал вычислений, исходы надзора и хеши материалов, включая engine и инспектор при отказе. Манифест принятого развёртывания не создаётся.
