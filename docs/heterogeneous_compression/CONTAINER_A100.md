# Контейнерный запуск пилота A100

04.11.2026 владелец повторно поручил использовать существующий SSH-доступ и прежний контейнерный способ запуска. A100 PCIe 40 ГиБ доступна через `hasboost-a100`. Перед подготовкой наблюдались 1 МиБ занятой памяти, 0% загрузки и пустой список вычислительных процессов.

Прежний блокирующий запрос прямого доступа к хосту относился к выбранной нами реализации через systemd. Для продолжения добавлен отдельный профиль с GNU `timeout`. Численный протокол пилота сохранён. Одна новая ResNet18/CIFAR-10 обучается 80 эпох на 40 000 изображениях, затем проверяются до 12 фиксированных рецептов с 200 восстановительными SGD каждый. Предельный расход составляет 27 440 SGD и 7200 секунд с учётом допуска и завершения. Random, Vreport и официальный test исключены из пилота.

## Внешний срок и процессы

`scripts/run_heterogeneous_container_pilot.py` создаёт новый каталог и исходную монотонную отметку времени. `/usr/bin/timeout` получает сигнал KILL и длительность, уменьшенную на резерв запуска и завершения. Его живой PID, время рождения, команда, PGID и системный таймер проверяются до CUDA. Отдельные supervisor, guard и единственный численный worker наследуют общую группу процессов. Supervisor и guard принимают осиротевших потомков, проверяют время их создания и сохраняют наблюдения. PDEATHSIG завершает дочернюю роль при исчезновении её непосредственного родителя.

Профиль рассчитан на фиксированный доверенный исполнитель и его обычных потомков. Ограничение группы процессов требует сохранения PGID. Обнаруженный выход потомка из группы вызывает завершение сохранённых собственных процессов. Произвольный внешний исполнитель, самостоятельно создающий другие сеансы, потребовал бы другой границы ОС.

## Контроль GPU

Перед запуском список GPU-процессов должен быть пустым. Worker подтверждает точный физический UUID через CUDA Driver API и сообщает о готовности. Наблюдатель допускает одну стабильную строку NVML. Дополнительная строка, смена PID, некорректная телеметрия или потеря наблюдения завершают собственный запуск. Неизвестный PID хоста сохраняется в журнале и участвует в проверках. Он не используется как цель сигнала внутри контейнера.

Связь одиночной строки с worker устанавливается по времени и рукопожатию. Доказательство соответствия PID хоста и контейнера здесь отсутствует. Квитанции содержат `host_pid_identity_proven=false`. Это ограничение учитывается при интерпретации стоимости пилота.

## Окружение и допуск

Отдельный каталог `/root/fedcore_heterogeneous_20261104` использует PyTorch 2.2.0+cu121, ONNX 1.16.2, ONNX Runtime 1.18.1 и TensorRT 10.0.1. До численного окна проверены импорты и `pip check`. Данные берутся из существующего локального CIFAR-10.

Внутри единственного окна сначала выполняются синтетические Dense и P→SVD→PTQ без SGD. Для инспектора TensorRT задаётся конкретная форма динамического входа. Его исходный вывод сохраняется и при отказе. После подтверждения экспорта, INT8-узлов и независимой загрузки начинается обучение M0. При отказе допуска или рецепта автоматического повтора нет.

Проверки контейнерного управления процессами выполняются отдельно на CPU. Качество и аппаратные результаты фиксируются только по квитанциям фактического пилота.
