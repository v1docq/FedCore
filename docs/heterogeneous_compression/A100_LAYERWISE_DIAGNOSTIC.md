# Послойная диагностика Q-only: подготовленный пакет

Цель — локализовать расхождение ONNX Runtime и TensorRT, воспроизведённое на 2000 калибровочных изображениях. Q-only остаётся непринятым; действующий допуск логитов `0.02 + 0.02*abs(ORT)` сохраняется. Этот документ описывает следующий отдельный запуск. Его подготовка выполняется на CPU; новое окно A100 ещё не запущено.

## Что установлено до запуска

Сохранённый ONNX содержит 128 узлов: 20 Conv, 32 QuantizeLinear, 48 DequantizeLinear и восемь остаточных Add. Проверка графа проходит; масштабы положительны и конечны, zero-point равны знаковому INT8 нулю, оси и размеры весов согласованы. Conv используют FP32 bias. Сырой TensorRT engine и ONNX имеют прежние хеши из [первого диагностического протокола](A100_QONLY_DIAGNOSTIC.md).

У четырёх Conv1 масштабы Q/DQ до и после ReLU различаются: `layer1.0`, `layer1.1`, `layer2.0` и `layer4.1`. В инспекторе эти операции входят в объединённые области. Это конкретные границы для проверки округления; инспектор не доказывает, какие округления выполнились внутри.

В исходном коде ONNX Runtime 1.18.1 обычный селектор QLinearConv требует DQ-родителей для фактических входов Conv. FP32 bias может препятствовать такому преобразованию. Поэтому оптимизированный граф CPU будет сохранён отдельно: до его проверки нельзя считать, что сравниваются две реализации целочисленной свёртки. [Исходный код ORT 1.18.1](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.18.1/onnxruntime/core/optimizer/qdq_transformer/selectors_actions/qdq_selectors.cc).

Установленный TensorRT 10.0.1 проверен чтением API при отключённой видимости CUDA, без создания контекста: `mark_debug` поддерживается, `mark_unfused_tensors_as_debug_tensors` отсутствует. Внутренний тензор должен быть отмечен до сборки engine. [Контракт TensorRT 10.0](https://raw.githubusercontent.com/NVIDIA/TensorRT/release/10.0/include/NvInferRuntime.h). Дополнительные выходы и отметки отладки могут изменить слияния; это ограничение учитывается в протоколе. [Документация NVIDIA](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/inference-library/engine-tools.html).

## Выбор изображений и наблюдаемых выходов

Используются восемь различных изображений из прежних calibration, без меток и новых оценок качества. Первые два воспроизводят исходную пробу. Ещё шесть выбираются среди восьми прежних расхождений argmax по убыванию разрыва двух ведущих логитов ORT; равенство разрешается по позиции в calibration.

Порядок train ID: `11, 20, 33848, 3998, 11666, 3192, 31270, 6088`. Он фиксируется по исходным парным логитам с SHA-256 `f2ce33689ff0647130bb293636b792615ea9e00a6b637a4c6e8946f2acd3337f`. Такая выборка диагностическая: она не представляет распределение качества CIFAR-10.

Отдельная копия ONNX получает 12 выходов: stem после ReLU, выходы восьми остаточных блоков после ReLU, pool, flatten и logits. Узлы, веса и масштабы исходного графа не меняются. Полные зависимости каждого выхода сохраняют обе ветви остаточного сложения и Q/DQ. Описания префиксов служат метаданными: отдельные префиксные engine не строятся.

Планируемые float32-выходы занимают 9 994 560 байт для восьми изображений у одного исполнителя. Общий объём сохраняемых массивов ORT и TensorRT ограничен 64 МиБ. Это размер наблюдаемых массивов, а не прогноз полной памяти GPU или сборщика.

## Этапы и бюджет

| Этап | Вычисления | Вызовы | Обработанные строки с повторами |
|---|---|---:|---:|
| Исходные ORT и engine | Пакеты `2+6`, восемь одиночных, один пакет из восьми для каждого исполнителя | 22 | 48 |
| Проверка привязки памяти | Исходный engine с новым контекстом, отдельным CUDA stream и проверенными адресами, пакеты `2+6` | 2 | 8 |
| Наблюдаемый граф | Дополненные ORT и TensorRT, пакеты `2+6` для каждого | 4 | 16 |
| **Всего** | **Восемь различных изображений** | **28** | **72** |

Из 72 обработанных строк 32 относятся к ORT, 40 — к TensorRT; это суммарный счётчик с учётом повторных диагностических вычислений.

Счётчик 28 относится к прикладным вызовам инференса. Служебные прогоны TensorRT при подборе тактик единственной сборки не используют выбранные изображения; их время входит в общий предел 600 секунд.

- Одно окно A100 до **600 секунд**, включая подготовку CUDA, единственную сборку и завершение. Для завершения резервируется 60 секунд; рабочий срок — 540 секунд от исходного старта.
- Одна сборка диагностического engine, одна копия ONNX с дополнительными выходами и до двух сохранённых оптимизированных графов ORT. TensorRT 10.0.1, Torch 2.2.0+cu121 и ORT 1.18.1 сохраняются.
- Профиль сборки совпадает с исходным: min/opt/max batch `1/128/128`, workspace 1 ГиБ, TF32 отключён. Веса и Q/DQ-параметры не переоцениваются.
- Нет SGD, нового поиска, экспорта обученной модели, повторной калибровки квантования, Vsearch, Vreport и официального test.
- Нет автоматических повторов. Каждая попытка вычисления и сборки записывается до вызова, завершение — отдельной записью.

Из общего двухчасового бюджета ранее учтено 1175,8133 секунды; остаток — 6024,1867 секунды. При расходовании всего нового окна останется не менее 5424,1867 секунды. Предлагаемые 600 секунд входят в этот остаток.

## Контроль достоверности

Сначала исходные engine и ONNX сравниваются на одинаковых изображениях при трёх способах пакетирования. Это проверяет небольшие пакеты; поведение batch 128 этим этапом не устанавливается.

Независимый путь привязки использует тот же сохранённый engine, новый execution context, отдельный CUDA stream, явную синхронизацию и проверку формы, типа, размещения, формата и адреса каждого тензора. Он не вызывает прежний `infer_device`. При несогласованности с прежним путём по действующему допуску запуск останавливается до сборки наблюдаемого графа.

Для дополненных графов отдельно сохраняются два контроля итоговых логитов на тех же пакетах `2+6`:

1. Дополненный ORT против исходного ORT.
2. Пересобранный TensorRT против сохранённого исходного engine.

Если дополнительные выходы меняют результат, промежуточные значения относятся к пересобранному диагностическому графу. Даже совпадение итоговых логитов не доказывает идентичность внутренних вычислений. Все наблюдаемые значения сохраняют эту маркировку; первый расходящийся выход диагностической копии не объявляется доказанной первой ошибкой исходного engine.

Порог промежуточных сравнений служит описанию ошибки. Он не вводит новый критерий аппаратной приёмки и не заменяет действующую проверку конечных логитов.

## Артефакты и условия остановки

В свежем каталоге сохраняются выбранные ID и входные массивы, все конечные логиты, 12 пар промежуточных массивов, ошибки и сводки по ним, план зависимостей, Q/DQ-параметры, оба оптимизированных графа ORT и операторы в них. Диагностические ONNX, engine и инспектор имеют собственные хеши. Исходные файлы сверяются до и после; manifest принятого развёртывания не создаётся.

Исполнитель использует прежний контейнерный профиль GNU timeout с ограничением `host_pid_identity_proven=false`. Перед запуском требуется свободная A100 с прежним UUID. Второй или изменившийся GPU-процесс, нарушение привязки UUID, несовпадение хешей/версий/данных, нечисловые выходы, превышение счётчиков, памяти или срока прекращают собственный запуск. Чужие процессы не останавливаются.

Результат этапа — подтверждённые границы расхождения и проверка влияния наблюдения на вычисления. Переход к продолжению восьми рецептов или основной серии эволюционного поиска не входит в этот диагностический пакет.

## Подготовленные команды

Команда ниже создаёт только статический план на CPU из сохранённых файлов:

```powershell
python scripts/plan_heterogeneous_layerwise.py --artifact-directory <saved-Q-only-artifact> --prior-pairs <logit-pairs.jsonl> --source-revision <clean-commit-sha> --output layerwise-plan.json
```

Для отдельного разрешённого запуска подготовлен фиксированный профиль существующего исполнителя:

```json
{
  "source_revision": "<clean-commit-sha>",
  "artifact_directory": "/root/fedcore_heterogeneous_20261104/run-02/pilot/recipes/Q_only/4fb0722e39b1fd3a8a0ad1cfefe3b6195feb25cd54694fe61f7cc7c90bb987d9/artifact",
  "profile": "layerwise_v1",
  "rows": 8,
  "batch_size": 8
}
```

Исполнитель — `scripts/run_heterogeneous_qonly_diagnostic.py`. Он принимает этот профиль только с восемью изображениями и пакетами до восьми, фиксирует 600 секунд и одну сборку; произвольная подмена лимитов через конфигурацию запрещена. Старый профиль сравнения логитов сохраняет предел 300 секунд и нулевой бюджет сборок.

Совместные локальные проверки подготовки: 159 успешных тестов и один пропуск. Включено настоящее сравнение исходного и дополненного небольшого ONNX-графа через ORT на CPU. Независимая проверка контрактов и ограничений не выявила блокирующих замечаний. Аппаратное исполнение нового профиля остаётся непроверенным до отдельного запуска.

На сервере с отключённой видимостью CUDA прошли все 160 CPU-проверок. Статические планы Windows и Linux совпали по выбранным изображениям, выходам, зависимостям и хешу дополненной ONNX-копии.
