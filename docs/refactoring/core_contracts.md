# Контракты основного API и локальной проверки

Изменения относятся к задачам #58–#64. Они сохраняют публичные шаблоны конфигурации и путь `FedCore`, но задают явные требования к данным, восстановлению модели и владению ресурсами.

## Конфигурация и зависимости

Версия берётся из `fedcore.__version__`; остальные метаданные, обязательные зависимости и дополнительные наборы определяет `pyproject.toml`. `setup.py` делегирует ему сборку, а `requirements.txt` устанавливает тот же пакет. Заявленный диапазон Python — 3.10 и 3.11. Дополнительные наборы `llm`, `gpu`, `export`, `service`, `vision` и `docs` устанавливаются отдельно; набор `test` содержит зависимости автономных проверок.

`ConfigFactory.from_template(T())` возвращает класс с независимыми значениями по умолчанию. Изменяемые вложенные значения копируются. `Literal`, `Union`, `Optional`, перечисления и элементы типизированных коллекций проверяются до запуска ресурсов. `MisconfigurationError` наследует `ValueError`; `exs` содержит причины, а отдельная ошибка может указывать `field`. `FedCore` повторно проверяет конфигурацию при создании и перед обучением. Недопустимые числовые настройки и неподдерживаемые режимы не запускают Dask и не меняют FEDOT.

## Модель и данные

Готовая `torch.nn.Module`, имя зарегистрированной модели или словарь контрольной точки задаётся через `CompressionInputData.model` либо `initial_assumption`. Контрольная точка имеет форму `{'path_to_model': path, 'model': template}` или `{'checkpoint_path': path, 'model_factory': factory}`; фабрика вызывается без аргументов. Если встроенное описание архитектуры достаточно, шаблон можно не передавать. Неподходящие ключи и формы весов вызывают `CheckpointError`.

`fit_no_evo` строит и обучает последовательность выбранных операций. `fit` использует FEDOT; именованные аргументы, включая `predefined_model`, передаются его методу `fit`. Исходная модель хранится отдельно. Готовая модель допускает `predict` до обучения. Режимы `original`/`default` выбирают исходную модель, `fedcore` — полученную после обучения; также поддерживаются `raw`, `labels`, `probs`, `model_before`, `model_after`.

Для оценки используются помеченные пакеты `(inputs, target)` выбранного источника. `get_report(data, split='val')` оценивает обе модели и собирает метки за один проход. При необходимости третий элемент пакета задаёт идентификаторы объектов; иначе идентификатором служит номер появления объекта в данном проходе. Перемешивание, размер пакета и неполный последний пакет сохраняют соответствие результатов и меток. Однопроходный источник допускается для оценки качества; дополнительные вычислительные метрики могут потребовать повторяемый `DataLoader`. Методы не меняют роли `train_dataloader`, `val_dataloader` и `test_dataloader`. Результат сохраняет двухуровневые столбцы `(0, mode)`.

Обёртка входных данных для FEDOT копирует модель и метаданные, сохраняя ссылки на уже заданные источники данных. Она не копирует генератор случайных чисел `DataLoader` и не создаёт новый поток выборки. Предсказания `BaseNeuralModel` передают метки, собранные вместе с выходами модели, в расчёт метрик.

## Локальные контрольные точки

Формат `fedcore.weights`, версия 1, содержит состояние модели, разрешённое описание архитектуры, режимы вложенных модулей и признаки `requires_grad`. Типы значений состояния ограничены тензорами, примитивными значениями и их контейнерами; сохраняются сведения `_metadata`. Квантованные тензоры записываются через целочисленное представление и параметры квантования, а типы данных — через разрешённые имена.

Автоматически восстанавливаются `Linear`, `Sequential`, `ReLU`, `Identity`, `Sigmoid`, `Tanh`, `Flatten`, `Dropout` и квантованные `Linear`. Для других архитектур, включая пользовательские классы и FX `GraphModule`, необходимо явно передать `model` или `model_factory`. Параметры операции допускают отдельные `model_factory_before` и `model_factory_after`. Отсутствие архитектуры вызывает ошибку вместо возврата непригодного словаря весов. Старое обычное состояние `state_dict` принимается только с явно заданной архитектурой.

Контрольные точки предназначены для локальных доверенных файлов. Они используют `torch.load(weights_only=True)`, но ограниченный загрузчик PyTorch 2.2 не является границей безопасности для недоверенных загрузок. Сервис обмена моделями должен использовать отдельный проверяемый формат и не передавать пользовательские файлы этому загрузчику.

`BaseCompressionModel.clear_model_cache()` освобождает ссылки на модели и сохраняет идентификаторы checkpoint. Следующее обращение к `model_before`/`model_after` восстанавливает модель. Проверка формата и совместимости предшествует изменению реестра; переданный шаблон не изменяется. `save` возвращает пути созданных файлов и сообщает ошибки сохранения. `load` восстанавливает модель из `model.pt` или явно указанного файла.

## FEDOT и Dask

Импорт `fedcore` и `fedcore.api.main` не подменяет методы FEDOT. `FedcoreModels` задаёт явную область адаптации, включая узкое разрешение известных операций сжатия в корне графа. Неизвестные операции проверяются исходным правилом FEDOT. Вложенные области восстанавливают точные предыдущие методы, дескрипторы и таблицы репозиториев. Они закрываются в обратном порядке в том же потоке. Блокировка удерживается до завершения области и исключает чередование областей FedCore из разных потоков.

Dask-клиент и кластер, созданные `FedCore`, закрываются после успешного обучения, ошибки или `KeyboardInterrupt`. `shutdown()` повторно не закрывает освобождённые ресурсы. Переданный через `dask_client` внешний клиент остаётся собственностью вызывающей стороны и не закрывается `FedCore`. Каждый новый запуск с внутренним клиентом создаёт собственные ресурсы.

## Проверки и пределы подтверждения

`tests/refactoring/test_core_contracts.py` использует настоящие импорты и публичные методы: независимость конфигураций, перемешанные данные классификации и регрессии, локальную тренировку, checkpoint, освобождение кэша, вложенную адаптацию и счётчики закрытия Dask. Имитаторы ресурсов нужны для проверки владения; математический расчёт, операция обучения и загрузчик checkpoint исполняются непосредственно.

`tests/refactoring/test_core_packaging.py` собирает wheel и sdist из отдельной копии исходников, пересобирает wheel из sdist, проверяет ресурсы и устанавливает wheel в отдельный каталог. Новый процесс вне checkout импортирует API и модуль devices, читает JSON и проверяет версию.

CI задаёт отдельные задания для Windows/Linux и Python 3.10/3.11 с автономным CPU-набором. Дополнительное задание устанавливает `export` и `service`. Наличие заданий не означает, что они уже успешно выполнены во всех средах. Полный старый набор тестов, внешние модели, GPU и большие LLM не входят в подтверждение автономной проверки.

Автономный профиль использует переданные пользователем `TensorDataset` и `DataLoader` с небольшими локальными моделями. Загрузчики внешних наборов данных и готовые архитектуры могут требовать отдельных библиотек, файлов или сети; успешная проверка этого профиля не подтверждает работу всех старых примеров.
